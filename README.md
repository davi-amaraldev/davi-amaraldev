## 💭 Engineering Questions I Care About

When I'm building something, I don't want to stop at:

> "It works."

I want to be able to answer:

<details>
<summary><b>Why does this class exist?</b></summary>

<br>

What responsibility does it own, and would another part of the application be a better place for that behavior?

</details>

<details>
<summary><b>Where should this business rule live?</b></summary>

<br>

In the controller? Service? Domain? Database?

Understanding ownership matters more than simply finding somewhere that compiles.

</details>

<details>
<summary><b>What happens when something fails?</b></summary>

<br>

Failures are part of the system.

Good backend engineering means thinking about invalid input, infrastructure failures, unexpected states and recovery.

</details>

<details>
<summary><b>How should this behavior be tested?</b></summary>

<br>

Tests shouldn't exist just to increase coverage.

They should protect behavior and give confidence when the system changes.

</details>

<details>
<summary><b>Will this code still make sense six months from now?</b></summary>

<br>

Readable and maintainable software matters just as much as software that works today.

</details>
